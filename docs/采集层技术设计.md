# LeoSentry · 采集层（Collector）详细设计方案

> 范围声明：本文档只覆盖"网络行为采集层"——conntrack 快照、NFT 流量计数、设备身份识别、DNS Map、数据存储流转。不涉及行为分类、策略判断、规则执行等后续层，那些留到后面单独讨论。
>
> 实现状态：本文档描述的功能已全部实现（见第 8 节代码结构对照）。实现过程中对原方案的修正与补充已直接写入对应章节，汇总见第 9 节修订记录。

## 1. 模块职责与产出

采集层只产出两个数据产物，本身不做任何判断/决策：

| 产出 | 内容 | 用途 |
| --- | --- | --- |
| 行为记录流 | 设备 / 目标IP / 域名 / 流量 | 后续分类与策略引擎的原始输入 |
| DNS Map | IP → 域名，带有效期 | 给行为记录"翻译"出人能看懂的域名 |

设计原则：

- 内核已经在维护的数据（conntrack 表、nft 计数器、ARP 表）只读，不处理任何网络包；
- 周期性快照 + 前后差分，而不是逐包记录；
- 每条记录只描述"一个采集周期内发生了什么"，不描述"一段会话从开始到结束"——会话/行为的拼接判断留给后续的分析层；
- 存储上"热数据在闪存、冷数据在硬盘"，角色严格分离；
- 程序依赖的系统设置（dnsmasq 日志、防火墙卸载、nft 表）全部由程序在启动时自动完成，不需要人工执行命令（见第 7 节）。

## 2. 数据采集

### 2.1 Conntrack：仅用于实时在线/活跃状态

- 库：`github.com/ti-mo/conntrack`（纯 Go，走 netlink，无需 cgo / 外部进程）
- **兜底来源**：若系统未安装 `kmod-nf-conntrack-netlink`（netlink dump 失败），自动回退为解析 `/proc/net/nf_conntrack`。两种来源都只取原方向五元组（协议、源/目的地址、源/目的端口），差分逻辑共用。两者都不可用时仅关闭实时在线状态，不影响历史记录。
- 周期：5～10 秒一次（可配置 `conntrack_interval`，默认 10 秒）
- 只统计原方向源地址属于受管网段的 IPv4 连接（即由家庭设备发起的连接）。
- 与上一次快照做差分，得到"新建 / 持续 / 结束"三种事件，用途是给 Web 面板提供"设备现在是否在线/活跃"这类**瞬时状态**展示（每台设备的当前连接数、本周期新建/结束连接数、最后活跃时间）。24 小时无连接的设备从状态表中移除。
- 不再用它来拼接"连接开始时间/结束时间"写进历史记录——历史记录的生成完全由 2.2 节的 nft 计数器驱动，两者是两个独立的消费场景，不绑在一起设计。

### 2.2 NFT 流量计数：历史记录的唯一数据源

- 库：`github.com/google/nftables`（netlink，原子批量提交）
- 所有对象放在 LeoSentry **独立的表 `inet leosentry`** 中，不改动 fw4 的 `inet fw4` 表，fw4 reload 不会冲掉这里的规则。程序启动时以单个原子批次删除并重建该表（所有计数器从零开始），正常退出时删除该表。
- 需要**两个独立的动态集合**，分别统计上行/下行，且 key 的字段顺序刻意保持一致（都是"设备IP在前、目标IP在后"），方便读出来后直接拼成一条记录。等价的 nft 语法如下（原方案写的 `map ... : counter` 不是合法的 nft 语法，按元素计数应使用"动态集合 + `update` 语句携带 `counter`"）：

```nft
table inet leosentry {
    set managed_devices {
        type ipv4_addr
        flags interval
        elements = { 192.168.1.0/24 }          # 受管网段，见下文
    }
    set traffic_up {
        type ipv4_addr . ipv4_addr             # key: 设备IP . 目标IP
        flags dynamic,timeout
        timeout 1h
        size 65535
    }
    set traffic_down {
        type ipv4_addr . ipv4_addr             # key: 设备IP . 目标IP（虽然包方向相反，key 顺序仍保持一致）
        flags dynamic,timeout
        timeout 1h
        size 65535
    }
    chain forward {
        type filter hook forward priority -10; policy accept;
        ip saddr @managed_devices update @traffic_up   { ip saddr . ip daddr counter }
        ip daddr @managed_devices update @traffic_down { ip daddr . ip saddr counter }
    }
}
```

- `managed_devices`：取配置项 `managed_network`（可多条 CIDR）；未配置时自动读取 `lan_device`（默认 `br-lan`）上的全部 IPv4 网段。
- 链优先级 -10 早于 fw4 的 forward 链（priority 0）。forward 钩子上，上行包的源地址仍是设备内网地址（SNAT 在 postrouting 才发生），下行包的目的地址已还原为设备内网地址（DNAT 反向在 prerouting 完成），因此两条规则都能拿到设备的真实内网 IP。
- **元素超时**：流量集合元素空闲 1 小时后由内核自动删除，被 `update` 命中时刷新超时，避免集合无限增长；集合满（65535）后新组合不再计数，但不影响转发。
- **流量卸载（flow offloading）冲突**：fw4 开启软件/硬件流量卸载后，已建立连接的数据包在 ingress 阶段走 flowtable 快速路径，不再经过 forward 钩子，计数器只能统计到每条连接最初的几个包。因此程序默认自动关闭流量卸载（配置项 `disable_flow_offload`，见第 7 节）。R2S 在关闭卸载后软件转发仍可接近千兆，家庭场景可接受。
- 周期：默认 60 秒（配置项 `collect_interval`），同时也是流量记录的时间粒度（见第 3 节"记录粒度与体积"）；conntrack 仍按 10 秒刷新实时状态。每次读取全部元素，与上次读到的绝对值相减得到本周期增量。**计数器只增不减，必须保存上次读数，不能把累计值当增量用。** 具体规则：
  - 上次没有、本次出现的元素：表在启动时重建、计数从零开始，且元素只可能在上次读取之后创建，因此当前值即增量；
  - 当前值小于上次值：元素超时被删除后又重新创建，把当前值当作增量；
  - 上次有、本次消失的元素：已超时删除，从上次读数中移除。
- 说明：这两个集合的 key 只有"设备IP . 目标IP"两个维度，不含协议（TCP/UDP）。也就是说协议这个维度在数据源头就已经被合并了，因此第 3 节的记录结构里不再保留 `Proto` 字段——留着也是拿不到真实区分的摆设。若以后确有需要按协议区分的场景，可以再给 key 加一维（`type ipv4_addr . ipv4_addr . inet_proto`），但目前判断"游戏/视频"这类行为并不依赖协议区分，暂不做。
- 当前只统计 IPv4。

### 2.3 设备身份识别：IP → MAC

采集到的连接/流量数据里，"设备"最初只是一个 IP，需要换算成稳定的 MAC 才能长期追踪同一台设备。数据来源：

1. **dnsmasq 动态租约文件 `/tmp/dhcp.leases`**（主要来源）：每行是 `到期时间 MAC IP 主机名 client-id`，用 `fsnotify` 监听变化，改动就整份重读（文件很小，全量重读无压力），另加 60 秒定时兜底重读。IPv6 租约与 `duid` 行忽略。
2. **`/etc/config/dhcp` 里的 `config host` 静态绑定**（补充来源）：给固定IP设备（打印机、NAS等）用，启动时读一次，之后监听文件变化并每 10 分钟兜底刷新。程序直接解析 UCI 文件，不 fork `uci` 进程。
3. **内核邻居表**（兜底与纠错来源）：读取 `/proc/net/arp`，只采用 Flags 含 `ATF_COM`（已解析出 MAC）的条目。每个采集周期刷新一次，内容未变化时不重建对照表。原方案计划用 `github.com/vishvananda/netlink` 的 `NeighList()`，实现改为直接读 procfs：数据来源相同（都是内核邻居表），省去一个依赖、减小二进制体积。

合并规则：静态绑定 < DHCP 租约 < 内核邻居表。租约与静态绑定提供主机名，并覆盖暂时没有通信的设备；**同一 IP 在邻居表中有已解析条目且 MAC 与租约不一致时，以邻居表为准**（它反映内核实际与之通信的二层地址，租约可能已过时），主机名按 MAC 从租约/静态绑定中继承。

合并结果是一张 `map[IP]Device{MAC, Hostname, Source}` 只读快照，通过原子指针发布，供 2.2 节生成记录时查表换算，采集热路径上不加锁。MAC 统一规范为小写冒号分隔格式。

**已知局限**：部分设备（iOS 14+ / Android 10+ / Windows 10+）默认对每个 Wi-Fi 网络使用随机 MAC。多数实现是"同一网络固定一个随机MAC"，长期识别同一设备通常够用；若设备开启"每次连接都换MAC"，会被误判为新设备，目前没有干净的技术解法，只能引导用户在孩子设备上为家庭 Wi-Fi 关闭随机 MAC。此问题记录在案，不在采集层解决。

### 2.4 DNS Map（IP → 域名）

- 数据源：**dnsmasq 查询日志**，不是 nftset（nftset 只把 IP 写进执行用的防火墙集合，不含域名字符串，不能当电话簿用）。
- 配置（由程序自动写入，见第 7 节）：

```
config dnsmasq
    option logqueries '1'
    option logfacility '/tmp/dnsmasq_query.log'
```

  注意：原方案写的是 `option logqueries 'extra'`，但 OpenWrt 的 dnsmasq 启动脚本按**布尔值**读取该选项（`append_bool "$cfg" logqueries "--log-queries=extra"`），值为 `'1'` 时才会生成 `--log-queries=extra`；写 `'extra'` 会被当作假值而**关闭**查询日志。

  **与 `/etc/dnsmasq.conf` 的冲突**：ImmortalWrt 25.12 自带的 `/etc/dnsmasq.conf` 含有 `log-facility=/dev/null`，而 UCI 的 `logfacility` 会在生成的配置中再写一次 `log-facility`。dnsmasq 遇到重复关键字会报 `illegal repeated keyword` 并**拒绝启动**，导致全网 DNS/DHCP 中断（实机部署时出现过）。因此程序在写入 UCI 前，先把该实例所用配置文件（`/etc/dnsmasq.<section>.conf`，不存在时为 `/etc/dnsmasq.conf`）中的 `log-facility` 行注释掉（行首加 `# `，行尾标注 `# disabled by leosentry`，原子写入）。

- 日志格式（extra 模式带流水号与客户端地址）：

```
Sep 26 14:00:00 dnsmasq[1234]: 5 192.168.1.10/53712 query[A] www.game.com from 192.168.1.10
Sep 26 14:00:00 dnsmasq[1234]: 5 192.168.1.10/53712 reply www.game.com is <CNAME>
Sep 26 14:00:00 dnsmasq[1234]: 5 192.168.1.10/53712 reply edge.cdn.net is 1.2.3.4
```

- 采集：`fsnotify` 监听日志文件变化（另加 1 秒轮询兜底），只读增量内容（记住上次读取的文件偏移量），不完整的行尾保留到下次拼接。按日志行首的流水号，把 `query[A]/query[AAAA] 域名` 和 `reply/cached/config/<hosts 文件> 域名 is 目标IP` 配对：
  - **CNAME 链归属**：同一流水号下 CNAME 链末端解析出的 IP 归属到用户**最初查询的域名**（上例中 `1.2.3.4 → www.game.com`，而不是 `edge.cdn.net`），这样后续分类看到的是用户实际访问的服务；
  - 兼容无流水号的旧格式：按"查询行 → 连续应答行"的顺序做同样的 CNAME 链归属（多客户端交错时可能出错，ImmortalWrt 25.12 默认为 extra 模式，不受影响）。
- **启动预热**：程序启动时从文件开头读取已有日志，以日志行内时间戳作为 `LastSeen`，超过有效期的条目会被正常淘汰。这样程序重启后无需等待设备重新查询 DNS 就能反查域名。
- **日志文件大小控制**：日志位于内存盘 `/tmp`，持续写入会耗尽内存。LeoSentry 是该文件唯一的消费者，读完后若文件超过 `dns_log_max_size_mb`（默认 8 MB）即**原地截断**为 0。不采用改名轮转，是因为：dnsmasq 运行在 procd ujail 中，日志文件被 bind mount 进 jail，改名或删除都会让 dnsmasq 继续写旧 inode；而 dnsmasq 以 `O_APPEND` 打开日志，原地截断后会自动从文件开头继续写。截断瞬间与读完之间可能丢失极少量行，只影响个别 IP 的域名反查，可接受。
- 存储结构：`map[目标IP] -> {Domain, LastSeen}`，有效期 30 分钟未刷新即视为过期（配置项 `dns_ttl`，避免 CDN 复用 IP 导致域名归属出错），每分钟清理一次过期条目。只记录 IPv4，与 nft 计数维度一致。
- 已知局限：设备用加密 DNS（DoH/DoT）时不可见；同一 IP 可能同时服务多个域名（以最近一次应答为准）；设备硬编码 DNS 服务器时日志无记录（后续可选旁听 53 端口作为增强，暂不实现）；**App 内置 HttpDNS 时同样不可见**——实测腾讯系游戏通过 HTTP 直连 DNSPod（如 `182.254.116.117:80`）解析游戏服务器地址，这部分目标 IP 在 dnsmasq 日志中完全不出现，记录的 `domain` 为空（实测某游戏设备约 58% 的记录无域名）。分析层识别游戏不能只依赖域名，需要结合 IP 段/ASN 名单，或在策略中封锁已知 HttpDNS 服务器 IP 迫使 App 回退到系统 DNS。开启 logfacility 后 dnsmasq 的其他日志（如 DHCP）也写入该文件，不再出现在 `logread` 中。

## 3. 记录组装

每个采集周期（默认 60 秒）结束时，遍历本周期内产生了流量增量的 `(设备IP, 目标IP)` 组合，流量不低于阈值的各生成一条记录（见下文"小流量过滤"）。字段命名遵循 Go 规范（驼峰、缩写词全大写如 `IP`/`MAC`），与数据库列（snake_case）一一对应：

```go
type UsageEvent struct {
    CollectedAt int64      // 采集周期统一时间戳（Unix 秒），对应列 collected_at
    DeviceMAC   string     // 经 2.3 节的 IP→MAC 对照表换算得到，设备的稳定标识；换算不到时为空串
    DeviceIP    netip.Addr // 记录时刻的设备IP
    TargetIP    netip.Addr
    Domain      string     // DNS Map 查得到就填，查不到留空（入库为 NULL），事后查到也可以补
    BytesUp     int64      // 本周期内的上行增量字节数（设备→目标）
    BytesDown   int64      // 本周期内的下行增量字节数（目标→设备）
}
```

- 原方案的 `Timestamp` 更名为 `CollectedAt`（列名 `ts` 更名为 `collected_at`）：语义更明确（"采集时刻"而非泛指的时间戳），且避免缩写列名。
- **时间戳对齐**：采集循环在 `collect_interval` 的整数倍时刻触发，`CollectedAt` 取对齐后的周期边界，一个周期内所有记录共用同一个值、不逐行取时间。对齐使程序在同一周期内重启时，重复写入能按唯一键合并（见 4.2 节）。
- IP 在内存中使用 `netip.Addr`（值类型、无堆分配、可直接作 map 键），MAC 使用规范化的小写文本；入库时两者都编码为整数（见 4.2 节）。
- **退出前补采**：程序收到退出信号时，先把当前不满一个周期的流量补采一次，时间戳取该周期的结束边界；重启后同一周期剩余部分的记录按唯一键与之合并，重启不丢数据。周期内的写库不受退出信号打断。
- `DeviceMAC` 为空的情况只出现在设备不与路由器二层直连（例如下挂了另一个路由器）时——直连设备通信时内核必然有其邻居条目。

**为什么不记录 StartTime/EndTime（会话式记录）**：早期设想是一条记录描述"一次连接从开始到结束"，但这要求连接结束前记录一直挂在内存里持续累加，长连接（比如挂几个小时的视频流）会导致数据迟迟不落盘、程序中途重启就丢数据，逻辑也更复杂。改成"每个周期一条独立记录、只含本周期的增量"之后：

- 永远是追加写入，不存在"未完成记录"需要后续更新的状态，程序随时重启都不丢历史；
- "今天用了多久"这类查询，直接把当天所有周期记录按设备/目标求和即可，不需要等连接"结束"才能统计；
- 一段完整"行为"（比如一次连续40分钟的游戏）由后续分析层看"同一设备同一分类连续多个周期都有记录"自行拼接判断，采集层不替它做决定，更灵活也更简单。

**`BytesUp` / `BytesDown` 的含义**：`BytesUp` 是设备发出的流量（上行），`BytesDown` 是设备收到的流量（下行）。分开记录是因为上下行比例本身是判断行为类型的线索——看视频/下载通常下行远大于上行，视频通话上下行接近，云盘同步/直播上行可能更大；合并成一个总数会丢失这个区分度。

每个周期的全部记录作为一个批次（`UsageBatch`）同时交给两个消费者：闪存上的 `today.db`（留痕）与内存中的当日累计计数器（高频查询）。

**小流量过滤**：一个周期内上下行合计低于阈值的 `(设备, 目标)` 组合直接丢弃，不写库、也不计入内存计数器（配置项 `min_flow_kb_per_min`，默认 8 KB/分钟，按采集周期折算；设为 0 关闭过滤）。过滤在分发给两个消费者之前完成，因此两者始终一致，程序重启后从 `today.db` 恢复的计数与重启前相同。这类流量主要是 App 心跳、推送保活、摄像头/智能设备的后台连接，保留它们会带来两个问题：一是行数暴增（见下表）；二是后台挂着的游戏 App 每隔几十秒发一次心跳，会被算成"活跃周期"，让游戏时长虚高。实机数据（一台正在对战的游戏设备 + 6 台普通设备）：

| 每分钟阈值 | 丢弃的行 | 丢弃的流量 |
| --- | --- | --- |
| 1 KB | 58% | 0.8% |
| 4 KB | 81% | 2.4% |
| **8 KB（默认）** | **87%** | **3.6%** |
| 16 KB | 91% | 5.6% |

游戏对战服务器（如 `ds-prod-*.df.qq.com`）的流量为每分钟 280 KB～1.5 MB，远高于 8 KB，不会被误过滤；视频流量更大。代价是设备总流量统计会偏少几个百分点，对"判断在做什么、用了多久"没有影响。

**记录粒度与体积**：采集周期即记录粒度，每个周期、每个 `(设备, 目标)` 组合最多一行。原方案为 10 秒，实机测得每分钟约 300 行、每行（含索引）159 字节，全天活跃时每天约 43 万行、69 MB，而 R2S 根分区可用空间仅约 80 MB。调整为 60 秒周期 + 小流量过滤 + 整数存储后，实测每分钟约 26 行、每行 92 字节，全天活跃时约 3.7 万行、3.5 MB。1 分钟粒度对"每天玩了多少分钟"这类时长配额已足够；家长关心的"及时断网"由策略层按内存计数器判断，最大延迟一个周期（1 分钟）。

## 4. 存储流转（闪存只存当天，历史归档到外部硬盘）

### 4.1 总体原则

- 闪存（eMMC / TF卡）**只保留当天数据**，不做长期堆积。
- 每天固定时间（默认凌晨 3 点，配置项 `rotate_at`）把刚结束一天的数据整体搬到外部硬盘归档，搬完清空闪存。
- 查询"最近1个月"的历史，直接读硬盘归档文件，不经过闪存，也不用 SQLite 常驻这部分历史。
- **统计日**：以每日切换时刻为界，即 03:00 至次日 03:00 算作一天。`today.db` 的切换、内存计数器的清零、归档文件的日期命名都以统计日为准，深夜 0～3 点的使用计入前一天，与家长对"今天"的直觉一致。
- **时区**：OpenWrt 没有 `/etc/localtime`，Go 运行时默认会退化为 UTC。程序按顺序取配置项 `timezone`、`system.@system[0].zonename`（如 `Asia/Shanghai`，二进制内嵌时区数据库）、`/etc/TZ` 中的 POSIX 串（如 `CST-8`，只取固定偏移）确定时区。

### 4.2 闪存侧：当天数据

用独立文件 `today.db`（默认位于 `/etc/leosentry/data/`；注意 OpenWrt 的 `/var`、`/tmp` 是内存盘，不能放这里），而不是"一张永久表 + 按行 DELETE"。表结构按 SQLite 惯例命名（表名复数 snake_case、约束与索引按 `前缀_表名_列名` 命名），并使用 `STRICT` 表做列类型校验：

```sql
CREATE TABLE usage_records (
    id           INTEGER PRIMARY KEY,         -- rowid 别名，无业务含义
    collected_at INTEGER NOT NULL,            -- 采集周期统一时间戳（Unix 秒）
    device_mac   INTEGER NOT NULL,            -- 设备稳定标识（48 位 MAC），无法换算时为 0
    device_ip    INTEGER NOT NULL,            -- 记录时刻的设备地址（IPv4，网络字节序），附加信息
    target_ip    INTEGER NOT NULL,            -- 目标地址（IPv4，网络字节序）
    domain       TEXT,                        -- DNS Map 查不到时为 NULL，允许事后补填
    bytes_up     INTEGER NOT NULL DEFAULT 0,  -- 设备→目标 字节增量
    bytes_down   INTEGER NOT NULL DEFAULT 0,  -- 目标→设备 字节增量
    CONSTRAINT uq_usage_records_collected_at_device_mac_target_ip
        UNIQUE (collected_at, device_mac, target_ip)
) STRICT;

CREATE INDEX idx_usage_records_device_mac_collected_at
    ON usage_records (device_mac, collected_at);

-- 供人工排查使用的可读视图（MAC/IP 还原为文本），程序本身不读取
CREATE VIEW v_usage_records AS SELECT id, collected_at,
    printf('%02x:%02x:%02x:%02x:%02x:%02x', ...) AS device_mac,
    printf('%d.%d.%d.%d', ...) AS device_ip,
    printf('%d.%d.%d.%d', ...) AS target_ip,
    domain, bytes_up, bytes_down
FROM usage_records;

-- 库文件元数据，如 day_start（本文件所属统计日的起始时刻，Unix 秒）
CREATE TABLE db_meta (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
) STRICT, WITHOUT ROWID;
```

设计要点：

- 主键用 `INTEGER PRIMARY KEY`（即 rowid 别名，纯行编号，无业务含义，插入最快）。原方案带 `AUTOINCREMENT`，已去掉：SQLite 官方不建议在不需要"编号永不复用"时使用它，它会额外维护 `sqlite_sequence` 表，每次插入多一次写。业务层面的唯一性交给 `UNIQUE (collected_at, device_mac, target_ip)` 单独约束——防止程序重启后重复写入同一周期数据。
- 写入使用 upsert，重复写入自动合并而非报错：

```sql
INSERT INTO usage_records (collected_at, device_mac, device_ip, target_ip, domain, bytes_up, bytes_down)
VALUES (?, ?, ?, ?, ?, ?, ?)
ON CONFLICT (collected_at, device_mac, target_ip) DO UPDATE SET
    device_ip  = excluded.device_ip,
    domain     = COALESCE(excluded.domain, usage_records.domain),
    bytes_up   = usage_records.bytes_up + excluded.bytes_up,
    bytes_down = usage_records.bytes_down + excluded.bytes_down;
```

  字节数累加而非覆盖：程序重启后 nft 表被重建、计数从零开始，同一周期内重启前后读到的是两段不重叠的增量。
- `device_ip`、`domain` 不参与唯一性判断，只是普通数据列：前者是设备当前地址（附加信息，身份认定看 `device_mac`），后者是查表得到的附加信息，允许后补。
- **MAC 与 IP 以整数存储**：MAC 为 48 位整数（`aa:bb:cc:dd:ee:ff` → `0xaabbccddeeff`），IPv4 为网络字节序的 32 位整数（`192.168.1.10` → `0xC0A8010A`）。文本形式的 MAC 占 17 字节、IP 占 7～15 字节，且唯一约束和索引各存一份；整数形式只需 4～6 字节，每行（含索引）从 159 字节降到 92 字节。用 `sqlite3` 排查时查询视图 `v_usage_records` 即可看到文本形式。
- 不含 `proto` 字段——见 2.2 节说明，当前 nft 集合的统计粒度里协议维度已被合并，留着是拿不到真实值的摆设。
- `db_meta.day_start` 记录本文件属于哪个统计日，程序启动时据此判断 `today.db` 是否已过期（见第 5 节）。
- **初始化只做一次**：表结构以迁移脚本形式内嵌在二进制中（`internal/store/migrations/*.sql`），版本号记录在 `PRAGMA user_version`。程序启动时、任何采集协程开始之前由 `store.Open` 完成初始化；已是最新版本时不做任何写入，每个迁移脚本在各自的事务内执行且只执行一次。每日切换新建的 `today.db` 同样在创建时初始化一次。以后调整表结构只需新增迁移脚本，不影响已有数据。
- 连接参数：`journal_mode=WAL` + `synchronous=NORMAL`（每次提交只顺序追加 WAL，显著减少闪存写入；断电时最多丢失最近一次提交），`busy_timeout=5000`，`temp_store=MEMORY`。每个采集周期的全部记录在单个事务内用预编译语句写入。
- **剩余空间保护**：每次写入前检查 `data_dir` 所在分区的剩余空间，低于 `min_free_mb`（默认 20 MB）时跳过本周期的明细写入并记录一次警告，空间恢复后自动继续写入并记录一次提示。内存计数器不受影响，Web 面板的"今天用了多久"照常可用。这样即使出现异常流量，也不会写满路由器根分区而导致 UCI 保存、软件安装等系统功能失效。

日切时**直接删除整个文件、新建空文件**，不用 `DELETE FROM` —— 避免 SQLite 删行不释放磁盘空间、需要额外 `VACUUM` 才能真正回收空间带来的闪存磨损。

今日高频查询（Web 面板每隔几秒刷新一次"今天玩了多久"）走**内存中的当日累计计数器**，不查 `today.db`；`today.db` 只用于落盘留痕和程序重启后恢复现场。计数器按设备、以及按设备+域名两级累计上下行字节与活跃时长（有流量的周期数 × 采集周期）；程序启动时从 `today.db` 汇总恢复。

### 4.3 硬盘侧：归档

- 每天生成一个归档文件：**直接把 `today.db` 复制一份到硬盘**，命名为 `archive_2026-09-26.db`（日期为统计日）——比导出成 CSV/JSONL 更省实现成本，查询时可以直接 `ATTACH DATABASE` 用 SQL 查，不用额外写解析逻辑。硬盘没有闪存那种擦写寿命顾虑，容量也远大于闪存，复制整份 db 文件的开销可以忽略。
- 复制前先把 `today.db` 切换为 `DELETE` 日志模式再关闭，触发检查点并删除 `-wal`/`-shm` 文件，保证磁盘上只剩单个完整的库文件。
- 复制先写入 `archive_<日期>.db.tmp` 并 `fsync`，再重新读取校验**大小与 SHA-256** 与源文件一致后改名为正式文件，最后删除闪存上的源文件。
- 归档目录：配置项 `archive_dir`，例如 `/mnt/sda1/leosentry_archive/`（需要用户在 ImmortalWrt 上预先挂载好外部硬盘）。**挂载检测**：读取 `/proc/mounts`，取归档目录路径前缀最长的挂载点，若该挂载点是 `/`、`/overlay`、`/rom` 或内存文件系统，判定为硬盘未挂载——此时 `/mnt/sda1` 只是闪存上的普通目录，绝不能往里写。
- **降级策略**：
  - 未配置 `archive_dir`：当天数据只留在闪存直到下一次切换，切换后丢弃；
  - 已配置但硬盘未挂载或复制失败：待归档文件保留在闪存上，每小时重试一次，超过 3 天仍未归档则丢弃，避免占满闪存；
  - 以上情况都通过归档状态（已配置/可用/最近一次归档时间与文件/最近错误）暴露给 Web UI，明确提示"未配置归档存储"或"归档硬盘未挂载"，不做静默失败。
- 保留策略：每次归档后顺带清理超过 30 天（配置项 `archive_keep_days`）的旧归档文件，按天滚动删除，逻辑简单。

### 4.4 查询路径

| 查询范围 | 数据源 |
| --- | --- |
| 今天 | 内存计数器（高频）/ 闪存 `today.db`（明细） |
| 最近1个月内某天 | 硬盘对应日期的 `archive_*.db`，直接 `ATTACH` 查询 |

## 5. 每日切换流程（默认凌晨 3 点，时段可配置）

1. 到达设定时段（建议选网络低谷时段，减少切换时的写入冲突）。切换在写入路径上触发：采集批次的时间戳跨入新的统计日时，先切换再写入，因此不需要单独的定时器，也不会出现"切换期间有批次写错文件"的竞争。
2. 采集程序把写入目标切到一个新的空 `today.db`（不中断采集）：关闭旧库 → 改名移入 `pending/usage_<日期>.db` → 新建 `today.db` 并初始化表结构、写入新的 `day_start`。整个过程在写锁内完成，耗时毫秒级。内存计数器在收到第一个新统计日的批次时清零。
3. 后台归档任务把 `pending` 中的文件复制到硬盘归档目录，按日期命名。
4. 校验复制成功（文件大小 + SHA-256）后，删除闪存上的旧文件。
5. 清理硬盘归档目录中超过保留天数的文件。

**程序在切换时刻未运行**（例如断电）：启动时 `store.Open` 发现 `today.db` 的 `day_start` 早于当前统计日，会先完成第 2 步的切换再开始采集，旧数据照常进入归档流程。

## 6. 数据流总览

```
conntrack dump（netlink / procfs 兜底）─► 快照差分 ─► 实时在线/活跃状态（仅内存，供 Web 面板即时展示）

nft traffic_up/down ─► 采集周期(60s，对齐，过滤小流量) ─► 按(设备IP,目标IP)生成 UsageEvent ─┬─► today.db（闪存，留痕）
                              ▲                                               └─► 内存当日计数器（高频查询"今天用了多久"）
                              │
IP→MAC 对照表 ────────────────┤（dhcp.leases / UCI 静态绑定 / /proc/net/arp 纠错）
                              │
dnsmasq 日志 tail ─► DNS Map(IP→域名) ─┘（查得到就填 Domain，查不到留空）

统计日切换（03:00）：today.db ─► pending/ ─► 复制到硬盘归档并校验 ─► 删除闪存旧文件；同时新建空 today.db
```

## 7. 系统自动配置（无需人工执行命令）

程序启动时自动完成以下系统设置。所有操作都是幂等的：先读取当前值，只有与期望不一致时才修改、提交并重启相关服务，因此重复启动不会反复重启 dnsmasq 或防火墙。非 OpenWrt 系统（找不到 `uci` 命令）上跳过并给出警告；单项失败只记录错误并以降级模式继续运行。

| 设置 | 等价命令 | 开关 |
| --- | --- | --- |
| 开启 dnsmasq 查询日志（对所有 dnsmasq 实例） | 注释 `/etc/dnsmasq.conf` 中冲突的 `log-facility` 行（见 2.4）<br>`uci set dhcp.@dnsmasq[i].logqueries='1'`<br>`uci set dhcp.@dnsmasq[i].logfacility='/tmp/dnsmasq_query.log'`<br>`uci commit dhcp && /etc/init.d/dnsmasq restart`<br>健康检查，失败则回滚 | `manage_dnsmasq` |
| 关闭 fw4 流量卸载 | `uci set firewall.@defaults[0].flow_offloading='0'`<br>`uci set firewall.@defaults[0].flow_offloading_hw='0'`<br>`uci commit firewall && /etc/init.d/firewall reload` | `disable_flow_offload` |
| 创建采集用 nft 表 | 等价于 2.2 节的 nft 脚本，通过 netlink 原子提交；退出时删除 | 始终执行 |
| ctnetlink 模块 | 内核在建立 ctnetlink 连接时按需自动加载 `nf_conntrack_netlink`；模块未安装时回退 procfs | 始终执行 |
| 时区 | 读取 `system.@system[0].zonename` 或 `/etc/TZ` | 配置 `timezone` 可覆盖 |

**dnsmasq 健康检查与回滚**：dnsmasq 承担全网 DNS 与 DHCP，改错配置的代价远大于缺少查询日志，因此重启后必须确认它真正在运行：

1. 重启后等待 2 秒，通过 `ubus call service list '{"name":"dnsmasq"}'` 读取各实例的 `running` 状态与 pid；
2. 再等待 6 秒复查一次，要求所有实例仍在运行且 pid 不变（排除"启动即崩溃、被 procd 反复拉起"的情况）；
3. 任一检查失败（实例未运行时日志中带上 `exit_code`）即按相反顺序撤销本次所有修改：恢复配置文件原内容、UCI 选项恢复旧值或删除，`uci commit dhcp` 后再次重启 dnsmasq，并以降级模式继续运行（无域名反查）。

**运行日志**：输出到标准输出，由 procd 转发到 syslog，级别为 `daemon.info`（此前写到标准错误，所有日志都显示为 `daemon.err`）。非终端运行时去掉 `time` 字段，避免与 syslog 自带时间戳重复。查看方式：`logread -e leosentry`。

**安装部署**同样由程序自身完成：把二进制拷到路由器上执行一次 `leosentry install` 即可，它会：

1. 把自身复制到 `/usr/bin/leosentry`；
2. 写入 procd 启动脚本 `/etc/init.d/leosentry`（`START=99`，晚于 dnsmasq 与防火墙；崩溃自动重启；修改配置文件后 procd 自动重启服务）；
3. `/etc/config/leosentry` 不存在时写入带注释的默认配置（已存在则保留用户配置）；
4. `enable` 开机自启并（重新）启动服务。

`leosentry uninstall` 停止并移除服务，保留配置文件与数据目录。

配置文件 `/etc/config/leosentry`（UCI 格式，全部可选，括号内为默认值）：

| 选项 | 说明 |
| --- | --- |
| `log_level` | 日志级别（`info`） |
| `data_dir` | `today.db` 所在目录，必须在闪存上（`/etc/leosentry/data`） |
| `archive_dir` | 外部硬盘归档目录，留空表示不归档（空） |
| `archive_keep_days` | 归档保留天数（`30`） |
| `rotate_at` | 每日切换时刻 / 统计日分界（`03:00`） |
| `timezone` | IANA 时区名，留空自动检测（空） |
| `collect_interval` / `conntrack_interval` | 采集周期，秒（`60` / `10`）；前者同时是流量记录的时间粒度 |
| `min_flow_kb_per_min` | 每分钟流量低于该值（KB）的 设备→目标 组合不记录，`0` 表示全部记录（`8`） |
| `min_free_mb` | `data_dir` 所在分区剩余空间低于该值（MB）时暂停写入明细，`0` 表示不检查（`20`） |
| `managed_network` | 受管网段，可多条 list；留空自动取 `lan_device` 的 IPv4 网段 |
| `lan_device` | LAN 接口（`br-lan`） |
| `dns_log_file` | dnsmasq 查询日志路径（`/tmp/dnsmasq_query.log`） |
| `dns_log_max_size_mb` | 查询日志截断阈值（`8`） |
| `dns_ttl` | DNS Map 条目有效期，秒（`1800`） |
| `leases_file` / `dhcp_config_file` | 租约文件 / DHCP 配置路径 |
| `manage_dnsmasq` / `disable_flow_offload` | 是否自动管理对应系统设置（`1` / `1`） |
| `http_port` / `http_address` | Web 页面端口（默认 `8088`，`0` 关闭）；监听地址留空则只用 `lan_device` 上的 IPv4 |

## 9. 修订记录

相对最初方案，实现时做了以下修正与补充：

1. **dnsmasq 配置**：`logqueries` 改为 `'1'`（OpenWrt 按布尔值解析，`'extra'` 会关闭日志），由程序自动写入并重启 dnsmasq。
2. **nft 语法**：`map ... : counter` 改为"动态集合 + `update @set { key counter }`"；所有对象放入独立表 `inet leosentry`；补充 `managed_devices` 的来源、元素超时与集合上限。
3. **流量卸载**：补充 flow offloading 会使计数失真的问题，默认自动关闭。
4. **字段命名**：Go 字段 `Timestamp` → `CollectedAt`，列 `ts` → `collected_at`；IP 字段使用 `netip.Addr`；唯一约束与索引按 `uq_/idx_ + 表名 + 列名` 命名；表使用 `STRICT`。
5. **主键**：去掉 `AUTOINCREMENT`，使用 `INTEGER PRIMARY KEY`。
6. **数据库初始化**：新增 `db_meta` 表与 `PRAGMA user_version` 版本化迁移，程序启动时一次性初始化；明确 upsert 的合并语义（字节累加、域名补填）。
7. **邻居表**：由 `vishvananda/netlink` 改为读取 `/proc/net/arp`；明确租约与邻居表冲突时以邻居表为准。
8. **conntrack**：增加 `/proc/net/nf_conntrack` 兜底来源。
9. **DNS Map**：补充 CNAME 链归属到原始查询域名、启动预热、日志文件原地截断（而非轮转）的原因。
10. **统计日与时区**：明确统计日以切换时刻为界；补充 OpenWrt 上的时区检测。
11. **切换与归档**：切换在写入路径上触发；增加 `pending` 目录、SHA-256 校验、挂载检测、重试与 3 天兜底丢弃；程序停机跨过切换时刻时启动即补做切换。
12. **部署**：新增 `leosentry install` 自动安装 procd 服务与默认配置。
13. **dnsmasq 配置冲突与回滚**（实机部署发现）：自动注释 `/etc/dnsmasq.conf` 中与 UCI `logfacility` 冲突的 `log-facility=/dev/null`；dnsmasq 重启后经 ubus 做两次健康检查，失败自动回滚全部修改。
14. **运行日志**：由标准错误改为标准输出（syslog 级别 `daemon.info`），非终端时省略重复的时间字段。
15. **已知局限补充**：App 内置 HttpDNS（如腾讯系游戏）绕过 dnsmasq，相应记录无域名，需由分析层以 IP 名单等方式补足。
16. **记录粒度与体积**（实机测得 10 秒粒度每天可达 69 MB，超过闪存可用空间）：采集周期默认改为 60 秒；新增小流量过滤 `min_flow_kb_per_min`（默认 8 KB/分钟），同时作用于写库与内存计数器；`device_mac`/`device_ip`/`target_ip` 改为整数存储并提供可读视图 `v_usage_records`；新增剩余空间保护 `min_free_mb`。实测每天约 3.5 MB。
17. **退出前补采**：退出时补采不满一个周期的流量并完成写库，重启不丢数据。
18. **Web 展示**（详见 [Web展示技术设计.md](Web展示技术设计.md)）：conntrack 忽略路由器自身 LAN 地址，避免把软路由算成一台上网设备。
